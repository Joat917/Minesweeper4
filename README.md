# 扫雷

纯前端的扫雷。两个模式：经典玩法，以及一个会显示每格含雷概率的辅助模式。

计算逻辑与界面完全分离——内核不认识 DOM，界面不认识游戏规则，概率算法是注入的第三方模块。

---

## 运行

```bash
python3 -m http.server 8000
# 打开 http://localhost:8000
```

**必须走 HTTP。** 用了 ES module，`file://` 下 `import` 会被 CORS 拦掉。

## 文件与依赖方向

```
index.html          结构
css/style.css       样式
js/minesweeper.js   游戏内核：无 DOM、无定时器、无随机源
js/probability.js   概率求解器：无 DOM、不认识内核
js/i18n.js          中英双语词条与 t()：无 DOM
js/ui.js            视图与交互：无游戏规则
js/solver.test.js   测试与基准，不参与游戏运行
```

```
ui.js ──> minesweeper.js
  ├────> probability.js
  └────> i18n.js
```

内核不 `import` 概率算法，而是从构造参数接收：

```js
new Minesweeper({ ..., assist: { analyze, resample } })
```

所以内核可以在 Node 里直接跑，不需要页面环境。

## 语言

中英双语，**没有语言切换入口**——跟随 `navigator.languages` 里第一个能识别的，zh 系归 `zh`、en 系归 `en`，都不是就用英文。

内核不认识任何语言：它返回的 `reason` 是**消息键**（如 `'reason.flagged'`），要填的参数放在同级的 `detail` 字段里，由界面用 `t()` 翻译。

```js
t('tools.start')                                   // '开始' / 'Start'
t('diff.frame', { name, rows, cols, mines })       // 占位符写成 {name}
```

取不到键时逐级回退：当前语言 → 英文 → 键本身。最后那层是有意的——界面上直接露出一个原始键，比静默空白好查。

`index.html` 里用三个标记：

| 标记 | 作用 |
|---|---|
| `data-i18n="key"` | 填 `textContent` |
| `data-i18n-aria="key"` | 填 `aria-label` |
| `data-i18n-title="key"` | 填 `title` |

分成三个是因为有些元素两种都要、内容却是动态的——计数器里是数字，只该改它的 `aria-label`，不能把数字覆盖掉。

加新语言：在 `js/i18n.js` 的 `DICT` 里加一份，`LANGUAGES` 和 `detectLanguage()` 各加一个分支。

## 玩法

### 经典模式

标准规则。

### 辅助 · 显概率

每格显示含雷概率（颜色 + 数字）。规则改动三处：

1. **翻开概率为 p > 0 的格子** → 综合胜率乘以 `(1 - p)`
2. **该格确实是雷，且 p < 1** → 重排布雷使该格为空，**已翻开的数字不变**，然后照常翻开
3. **p = 1** → 不存在合法重排，正常踩雷结束

**综合胜率 = ∏(1 - pᵢ)**，也就是"一个没有这套保命机制、纯靠运气的玩家走到现在还能活着的概率"。p = 1 时因子为 0，自动归零。

第 3 条不是补丁，是数学边界：p = 1 意味着该格在所有一致方案里都是雷，"重排布雷且不改动已翻开数字"无解。所以"p = 1 才死"是唯一诚实的分支。

和弦展开（一次掀开多格）按**逐格最优点击**计价：每轮从待开格里挑当前概率最低的，按 `(1 - p)` 计入，翻开、拿到新约束，然后**重新评估**剩下的格子，重复到开完。直接连乘各格的概率会显著高估风险，因为那些是边缘概率、彼此不独立。

### 键位

鼠标端：

| 操作 | 动作 |
|---|---|
| 左键 | 翻开 |
| 右键 | 插旗 |
| 中键／点已翻开的数字 | 和弦展开 |
| Shift ＋ 笑脸 | 复现上一局 |

触摸端**反过来**：

| 操作 | 动作 |
|---|---|
| 单击 | 插旗（点在已翻开的数字上是和弦展开） |
| 长按 | 翻开 |

键盘：

| 操作 | 动作 |
|---|---|
| 方向键 | 移动光标 |
| 空格 | 翻开／和弦展开 |
| F | 插旗 |
| R | 重开 |

把"翻开"放在长按上，是因为它是这一局里唯一不可撤销的动作——点歪一格就可能直接踩雷。插旗随时可以取消，所以放单击上。

## 概率求解器

契约写在 `js/probability.js` 顶部。两个纯函数：

```js
computeProbabilities(view, options) -> ProbabilityResult
sampleLayout(view, forbidden, options) -> LayoutResult
```

`view` 只包含**已翻开的格子和它们显示的数字**——不含旗子，也不含任何雷的位置。旗子只是玩家备忘，不参与计算。

数学定义：设 `S` 为所有"恰好 M 颗雷、且与全部已翻开数字一致"的布雷方案，则

```
p(c) = |{ L ∈ S : c ∈ L }| / |S|
```

关键推论：

- `p = 0` ⟺ 该格在所有一致方案里都不是雷
- `p = 1` ⟺ 该格被逻辑强制 ⟺ 不存在让该格无雷的一致方案
- `Σ p = M`，可作实现的整体自检

实现是一条递归：化简 → 拆块 → 枚举拆分 → 收口。详见文件内的注释。

## 测试

在页面控制台里：

```js
await import('./js/solver.test.js')   // 装载一次，不自动跑
solverTest.runAll()                    // 想跑几次跑几次
```

五节：锚点、与暴力枚举对拍、采样合法性、求解基准、重排耗时。

**为什么不能自动跑**：ES module 按 URL 缓存，`import()` 第二次拿到的是缓存、模块体不再执行。所以模块体只负责把入口挂到 `globalThis.solverTest`。

改过测试文件本身之后，用时间戳地址强制重载：

```js
await import('./js/solver.test.js?t=' + Date.now())
```

快速档：

```js
solverTest.runAll({ samples: 50, rounds: 8, budget: 8000, capMs: 8000 })
```

## 缓存

`index.html` 里的 `css/js` 引用都带 `?v=N`。**改完 js 或 css 要把这个数字 +1**，否则浏览器可能拿启发式缓存里的旧文件（`python -m http.server` 不发 `Cache-Control`）。

`js/solver.test.js` 顶部的 `?v=N` 要和 `index.html` 保持一致，否则测试跑的是另一份代码。

## 几个不显然的设计点

**雷图是 `(seed, 首点)` 的函数，不是 `seed` 的函数。** 因为"首点必定开出 0"要求落雷时避开首点的 3×3 邻域，候选池随首点位置而变。所以复现同一局必须同时复用种子和首点——`Shift+笑脸` 做的就是这件事（它会自动补做同一次首点）。

**辅助模式下概率是全盘耦合的。** 全局那条「总雷数 = M」把所有未翻开格子绑在一起，所以翻开任何一格、拿到新数字，都会改变**其余每一格**的条件概率。因此辅助模式每次操作都整盘重画，不能只重画状态变了的那几格。

**格子尺寸的链条是单向的**：

```
屏幕尺寸 + 棋盘行列数  →  格子边长  →  显不显示百分比数字
   fitBoard() 唯一决策    board--roomy      CSS ::after
```

想调数字的可见性就调阈值（`MIN_PROB_FONT`），不要去动格子边长的算法。

**重排不会破坏概率计算的前提。** 点一个有风险的格子有两个走向——本来不是雷就直接翻开；本来是雷则从"该格无雷"的一致方案里均匀抽一份——两者给出的后验是**同一个分布**。所以"当前雷图在已翻开信息下均匀分布"这个前提始终成立，引擎不需要知道有没有发生过重排。

**窄屏上宽扁的棋盘会自动转 90°。** 手机是竖长的，而高级盘是 16 行 × 30 列。横着塞进竖屏只能压到格子尺寸下限然后横向滚动；转过来变成 30 行 × 16 列，正好贴着手机长边。判据在 `computeRotation()`，三个条件缺一不可：窄屏（视口 ≤ 640px）、列数 > 行数、列数 ≥ 30。

实现上是**真正把网格转置**（重建 DOM 时按视觉行列重排），不是 CSS `rotate(90deg)`——后者会把格子里的数字一起转歪。方向键也跟着按视觉方向走。

**`fitBoard()` 靠测量反推可用高度**（`app 总高 − 棋盘区高`），所以任何会让"棋盘之外的高度"随棋盘宽度变化的东西都会造成震荡。`.hint` 上的 `max-width` 就是为了这个，不是装饰。
